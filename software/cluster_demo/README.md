# CANHACK 驾驶演示

网页演示台通过本机 Python 服务连接 PCAN。左侧操作发送训练用 CAN 帧，驱动确认发送成功后同步更新驾驶画面。Flipper 捕获后重放时，车速表、转向灯和车门状态也会随 PCAN 收到的帧变化。所有通道默认联动，不需要额外开启预览。

Three.js 路面、草地、路肩、标线和路侧物件使用同一个车速位移推进。地面采用带纹理的循环几何分段，与树木和阴影共同移动；纹理不再单独反向滚动。驾驶视角保持固定，加减速只改变行进速度。

场景全部本地程序化生成：阔叶树按分叉枝干骨架在外侧细枝上连续布置叶簇，分阴影、中间调、受光三层绘制；另有针叶树（暗色树芯加下垂针叶层）、路侧灌木、草地岩石、百米桩和沿线电线杆。路面带轮迹磨暗、车道中央油渍和沥青补缝，草地有裸土斑块与野花。对向车道有车流驶过（本车静止时也会经过，随机车速与车色），远处山脊有缓慢转动的风力发电机，后视镜中同样可见。开发调试时可打开 `/texture-test.html` 单独查看全尺寸树木纹理。

默认报文映射取自 `refer/ICSim`，用于演示，不对应量产车型。

| 状态 | CAN ID | 数据位置 |
| --- | --- | --- |
| 车门锁 | `0x19B` | byte 2，bit 0-3 对应四扇门，置 1 为锁定 |
| 转向灯 | `0x188` | byte 0，bit 0 左转，bit 1 右转 |
| 车速 | `0x244` | byte 3-4，ICSim mph 编码，界面显示 km/h |
| 胎压 / 温度 | `0x5A0` | 自定义演示报文，格式见下方 |
| 自动制动状态 | `0x5A1` | 自定义演示报文，格式见下方 |

## 启动

1. 安装 Python 依赖：`python -m pip install -r requirements.txt`
2. 安装 PEAK 驱动；PCAN 与 Flipper 使用相同波特率，默认 `500000 bit/s`。
3. 将 PCAN 与 Flipper CAN 扩展板接入同一条 CANH/CANL/GND 总线，并按总线拓扑设置终端电阻。
4. 双击 `run_demo.bat`。首次启动会安装网页依赖，每次启动会构建网页；服务就绪后自动使用默认浏览器打开 `http://127.0.0.1:8765`。演示期间保留启动窗口，按 `Ctrl+C` 停止服务。如果浏览器未能自动打开，可手动访问该地址。

网页开发时，可在本目录分别运行 `python server.py` 与 `npm run dev`，再打开 Vite 显示的本地地址。
直接运行 `python server.py --open-browser` 也会在服务就绪后打开浏览器；不加该参数则只启动服务。

点击右上角齿轮打开“连接与车辆设置”，CAN 通道、波特率、ESP32 串口和低胎压阈值都在这里配置。连接按钮立即连接 / 断开设备；“应用设置”提交胎压阈值，桥接进程重启后恢复默认值。关闭设置后，主页面只保留驾驶控制、仿真和 CAN 日志。

没有设备时选择 `virtual` 通道即可离线操作。PCAN 与虚拟通道使用相同的联动逻辑：操作、ESP32 胎压转发和自动制动产生的 TX 帧在驱动确认发送成功后更新仪表，收到 RX 帧也更新仪表。TX 成功表示本机驱动接受发送，不表示 Flipper 已完成捕获；Flipper 重放仍通过 RX 接收。接收报文不会被自动转发回总线。

## 演示流程

1. 在右上角设置中选择 PCAN 通道和 `500 kbit/s` 后连接。
2. Flipper 打开 CANHACK 的 `Capture`。出现 `REC` 后，在网页端操作车门、转向灯或车速。
3. 捕获期间网页画面同步响应操作，右侧记录电脑发出的 TX 帧。
4. 在 Flipper 按 Back 结束捕获，进入 `Replay`，选择 `Real` 并打开刚保存的日志。
5. Flipper 重放帧到总线后，右侧出现 RX，驾驶视图根据收到的帧更新。

车门快捷键：`1-4`。转向快捷键：`Q` 左转、`E` 右转、`H` 双闪。按住 `W` 加速、按住 `S` 制动；`U` 全部解锁，`L` 全部上锁。

## 后台 UDS 模拟 ECU

网页后端连接 CAN 后会自动运行一个独立的 UDS 模拟 ECU，不需要额外开关，也不改变驾驶画面。它使用同一条 PCAN / virtual 总线，仅响应诊断请求，空闲时不主动发送报文。关闭网页后，已连接的 CAN 和 UDS ECU 继续运行；点击“断开”或停止 Python 服务后关闭。重新打开网页会显示仍连接的通道。

更新后先执行 `python -m pip install -r requirements.txt`，安装新增的 `can-isotp` 依赖。模拟 ECU 使用经典 CAN、标准 11 位 ID、ISO-TP 普通寻址：请求 **`0x721`**，响应 **`0x728`**，与 CANHACK 默认设置一致；波特率跟随网页选择，默认 **500 kbit/s**。VIN 等长响应先发 First Frame，收到测试端 Flow Control 后才发 Consecutive Frame，支持块大小和最小帧间隔。

| UDS 服务 | 演示行为 |
| --- | --- |
| `0x10` DiagnosticSessionControl | 默认 / 编程 / 扩展会话（`01 / 02 / 03`），返回 P2 / P2* 参数 |
| `0x3E` TesterPresent | `00` 返回应答，`80` 保持会话并抑制正响应；5 秒没有诊断请求则回默认会话 |
| `0x22` ReadDataByIdentifier | 读取下表数据，支持一条请求包含多个 DID |
| `0x19 01 / 02` ReadDTCInformation | 按状态掩码读取故障码数量 / 列表，初始有两条模拟记录 |
| `0x14 FF FF FF` ClearDiagnosticInformation | 清空模拟故障码，再读取时数量为 0 |
| `0x11 01 / 02 / 03` ECUReset | 只复位模拟 ECU：恢复默认会话及两条初始故障码，方便重复演示 |

| DID | 返回值 |
| --- | --- |
| `F186` | 当前会话：`01 / 02 / 03` |
| `F187` | 零件号 `DEMO-ECU-001` |
| `F189` | 软件版本 `1.0` |
| `F18A` | 厂商 `CANHACK` |
| `F18C` | 序列号 `DEMO0001` |
| `F190` | 17 字符模拟 VIN `CANHACKDEMO000001` |
| `F191` | 硬件版本 `HW-DEMO-01` |

CANHACK 演示建议：

1. 连接 PCAN，Flipper 的 CANHACK 波特率设置为 500 kbit/s、晶振设置与扩展板一致。
2. 在 `UDS Services → Settings` 确认 REQUEST ID 为 `0x721`、RESPONSE ID 为 `0x728`。
3. 使用 `ECU Info / VIN` 直接展示完整 VIN、软件版本等；在 `DID Scanner` 选择会话和 `Quick ID (F180-F1A0)`，扫描全部演示 DID。CANHACK 已支持完整 ISO-TP 长响应，未知 DID 的 NRC 31 不计为发现。扫描完整 HEX/ASCII 数据会保存到 Flipper 应用数据目录的 `logs/DID_*.txt`。
4. 使用 `Read / Clear DTC` 展示两条模拟故障码，确认清除后再次读取为 0 条。再使用 `ECU Reset → Default (0x01) → Hard Reset` 展示模拟复位，恢复两条故障码。网页 CAN 日志可直接看到请求 RX 和 ECU 响应 TX；诊断处理不依赖网页保持打开。
5. 展示 `ECU Discovery` 时可将范围缩到 `720–730`；发现后选择 `721 → 728` 自动应用地址。默认每 ID 等待 10 ms，主机调度较慢时可改为 50 或 100 ms。

故障码案例的数据为 `123456 / 状态 09`、`ABCDEF / 状态 08`，均为固定模拟记录，与车辆画面无关。诊断测试端发送 UDS 载荷 `19 01 FF` 可读到数量 2，`19 02 FF` 可读到列表；`14 FF FF FF` 清除后再读为 0；`11 01` 或断开重连后恢复为 2。以上是 UDS 载荷，通过 CAN 发送时需加 ISO-TP PCI，例如读数量的完整 8 字节帧为 `03 19 01 FF CC CC CC CC`。

不支持的服务、子功能、DID 和错误长度分别返回 NRC `11 / 12 / 31 / 13`。安全访问、刷写和真实内存访问未实现；模拟数据全部保存在内存中，连接重建时恢复默认值。实现位于 `demo_uds.py`，自动回归通过虚拟 CAN 覆盖真实后端收发、多帧请求/响应、流控、会话超时、故障码清除及连接重置。

## 胎压显示

仪表盘中央围绕车辆俯视图显示四轮压力和温度，初始值均为 **2.6 bar、26°C**。默认值只用于画面，不自动发送 CAN 帧；实际串口 / CAN 数据到达后覆盖对应轮位。桥接进程运行期间，刷新网页会恢复最近收到或成功发出的胎压值。低胎压报警位于中央屏底部，报警时车辆图与四轮数值仍保持显示。

串口接收和 CAN 转发已实现，数据路径为：

**Flipper 433 MHz → CC1101 / ESP32 解码 → USB 串口 → Python 桥接 → PCAN 发送 `0x5A0` → 总线日志和仪表更新。**

1. 安装 `requirements.txt` 中的依赖（包含 `pyserial`），启动本机服务。
2. 在右上角设置中先连接 PCAN，再在“胎压接收”中刷新并选择 ESP32 的串口，点击连接。串口固定为 **115200、8N1**。
3. ESP32 每次解出一个轮胎的数据，输出一行 UTF-8 JSON，以 `\n` 结束。串口读取会拼接分段数据，并忽略启动日志、无效 JSON 和超长行。
4. 有效数据编码后立即通过当前 CAN 通道发送；只有发送成功才产生 TX 日志并更新仪表。发送失败或串口断开会停止串口接收并在设置页显示原因。断开 / 切换 CAN 时也会关闭串口，需要手动重新连接。
5. 总线上收到同格式的 `0x5A0` RX 帧会更新对应轮胎，**不会再次转发**。Flipper 捕获并重放即可触发相同显示。

ESP32 串口输出格式：

```json
{"type":"tpms","wheel":"fl","pressure_bar":2.6,"temperature_c":26}
```

`wheel` 使用 `fl`（左前）、`fr`（右前）、`rl`（左后）、`rr`（右后），传感器 ID 与轮胎位置的对应关系由 ESP32 配置。压力统一换算为 bar，温度为摄氏度，两个字段使用 JSON 数字。单轮更新保留其余三轮的值；无效轮位、非数字或超出范围（0–10 bar、−50–150°C）的消息会被忽略。

`0x5A0` 使用标准 11 位 CAN ID、8 字节数据。它是本项目的演示协议，不对应任何量产车型。

| 字节 | 含义 |
| --- | --- |
| 0 | 轮位：0 左前，1 右前，2 左后，3 右后 |
| 1–2 | 压力，uint16 小端，单位 0.01 bar（数值也等于 kPa） |
| 3–4 | 温度，int16 小端，单位 0.01°C，支持负温度 |
| 5 | 发送序号，0–255 循环，不作为重放拦截条件 |
| 6 | 保留，固定 0 |
| 7 | 协议版本，固定 1 |

例如左前 **2.6 bar / 26°C**、序号 0：`5A0 [8] 00 04 01 28 0A 00 00 01`。Python 编码位于 `protocol.py`，网页解码位于 `web/src/tire-pressure.js`。

ESP32 固件位于 `tpms/esp32_tpms_cluster/esp32_tpms_cluster.ino`（单文件收发一体，433.920 MHz、2-FSK、TPMS OTA 帧格式），一台 ESP32 + CC1101 同时扮演四轮传感器与车身接收端，模拟真实车辆 TPMS 行为：

- **加速和减速**：Web 油门、刹车、滑杆、自动制动和 CAN 收到的车速经桥接写入 `SPD <kph>`。变化达到 1 km/h（包含恰好 1）就请求一轮四轮 burst；相邻轮次起点至少间隔 3 s，期间的变化合并为下一轮。相同速度的串口心跳不会触发新 burst。
- **无速度变化（含停车）**：每 **20 s** 发送一轮，以轮次开始时间计时；速度变化触发的发送重新开始计时。固件启动后先发一轮。
- **发送值与仪表同步**：每次模拟发送固定使用原始压力 189（2.594 bar，仪表显示 **2.6 bar**）及 **28°C**。本机无法接收自身的 RF 发射，因此发送成功后通过串口输出 `source: "tx"` 的 JSON（`rssi: null`），经 CAN `0x5A0` 同步仪表。收到的值可能是伪造值；下一次成功模拟发送会用上述默认值覆盖它。发送失败不产生成功同步值。
- **接收**：每个射频包发送后立即恢复 RX；四轮按轮位轮流发送，每轮重复 6 次，包间隔至少 40 ms，间隔中也接收。GDO0 边沿中断持续采集，不等待 RSSI 达到阈值后才开始采样。仅将前导字节、CRC、数值范围和绑定 ID 都有效的帧输出为 `source: "rx"`，实时更新对应车轮；其他 ID 不映射到仪表。相同值的重复接收在 1 s 内合并，不影响压力/温度变化的即时更新。
- **串口重连/重启**：桥接保存当前车速，连接时发送，并每秒补发；固件输出 `[READY]` 时立即重新同步。串口写入有超时且串行执行，失败会显示在设置页并重试。

首次启动左前 ID 为 `2D1D11C0`，其他三轮随机生成，四轮 ID 均保存到 ESP32 NVS；以后重启保持不变。串口命令（115200、以换行结束）：

```text
IDS                   查看四轮 ID
ID fl 2D0DC0C0        将左前绑定到指定传感器 ID，并保存到 NVS
SPD 30                模拟车速 30 km/h
SPD 0                 减速到零（仍然每 20 s 周期发送）
TX                    请求一轮发送（也遵守最小 3 s 间隔）
SHOW                  查看状态
```

`ID` 可选轮位为 `fl/fr/rl/rr`，ID 必须为 8 位十六进制，不能为全零、全 F 或与其他轮位重复。参考 TX 项目的默认 ID 是 `2D0DC0C0`，与本项目默认左前 ID 不同，联调时要显式绑定；实体传感器则使用其实际空口 ID。用串口监视器配置前先在网页断开 ESP32，配置后关闭监视器并重新连接网页。配置保存后无需每次重做。

联调步骤：

1. 使用 ESP32 Arduino Core 编译并刷入 `tpms/esp32_tpms_cluster/esp32_tpms_cluster.ino`。CC1101 接线：GDO0→13、GDO2→4、CSN→5、MOSI→23、MISO→19、SCK→18，供电 3.3 V；接收中断使用 GDO0，务必接好。
2. 网页先连接 CAN（没有 PCAN 时可选虚拟总线验证页面链路），再选择 ESP32 串口。启动或下一个 20 s 周期应见四轮 `0x5A0` 更新为 2.6 bar / 28°C。
3. 分别加速、减速、停车，检查 `[TX] burst start (speed-change)`；持续操作时轮次至少间隔 3 s。停止操作后检查 20 s 周期以及 RX 心跳中的 `MARC=0x0D`。
4. 用同制式传感器或参考发送器发送已绑定 ID 的帧，应立即更新相应轮位；错误 CRC 或其他 ID 不应更新。随后下一轮成功模拟发送恢复默认值。低压帧会触发演示制动，而制动本身也会产生减速触发发送，因此默认值可能在 20 s 前就覆盖低压值。
5. 用另一台接收器或 SDR 检查发射的 433.920 MHz、2-FSK、约 52 µs chip 的 TPMS 帧。一个 CC1101 是半双工，实际发射及模式切换期间仍会漏接同时到来的帧；普通 TPMS 传感器通常负责发射，不会对本机 433 MHz 发射自动应答。只有频率、调制和协议匹配的传感器才能由本固件解码。

回归检查（在本目录执行）：

```text

g++ -std=c++17 -I tests/firmware_stubs tests/firmware_test.cpp -o firmware_test

```

## 低胎压自动制动

后端根据实际收到的 `0x5A0` 帧（包括 ESP32 成功转发的帧）判定胎压；四轮默认显示值不参与判定。任一轮胎 **低于 2.0 bar** 时，中央仪表点亮黄色轮胎截面 / 感叹号警告灯，显示“胎压过低”和异常轮位，对应轮胎的压力、温度、轮位文字和示意图标红。**温度达到 80°C** 也会将对应轮胎标红，但不触发制动。

低胎压同时启动演示 ECU 制动：通过 PCAN 发送 `0x5A1` 制动状态，再按约 **18 km/h 每秒**降低 `0x244` 车速，每 100 ms 更新一次，直到停车。停车期间每秒发送零车速和制动保持状态。仪表和道路场景跟随减速；制动期间禁用手动车速控制，并忽略重放的增速帧对仿真车速的影响。制动只由后端执行，多浏览器不会重复启动发送任务。

报警阈值可在设置页调整（0.5–3.0 bar）。已报警轮胎必须恢复到阈值以上 **0.2 bar** 才解除，默认即 **2.2 bar**，避免临界值附近反复制动。全部低压轮胎恢复后发送解除帧，不恢复之前的目标车速。发送失败会在中央仪表显示“制动发送失败”；断开 CAN 或关闭最后一个网页会停止发送。

`0x5A1` 为标准 11 位 ID、8 字节，是本演示的制动状态协议，不是量产车制动执行器指令。

| 字节 | 含义 |
| --- | --- |
| 0 | 制动保持：1 开启，0 解除 |
| 1 | 演示制动请求：100 开启，0 解除 |
| 2 | 低压轮位位图：bit 0–3 为左前、右前、左后、右后 |
| 3–6 | 保留，固定 0 |
| 7 | 协议版本，固定 1 |

仪表采用左侧车速表、右侧转速表、中央方形信息屏的布局。中央默认显示车辆俯视图及四轮胎压、温度；时间与挡位固定显示，底部显示本次行程。点击信息屏顶部“行程”可查看行驶时间、平均车速和门锁状态。车门解锁时，俯视车身对应位置亮起。低胎压报警期间自动回到胎压页并锁定，底部显示报警，四轮数值保持可见。

仪表总成居中固定为 800 px 宽，空间不足时随窗口缩小；表盘、字体和间距都按仪表自身宽度计算。全屏或宽屏时扩展窗外视野，仪表不会沿屏幕横向拉开。

座舱采用深灰皮纹台面、缝线遮光罩、下沉表圈与金属饰条。场景宽度达到 1100 px 时，两侧显示窗框、出风口和后视镜；较窄的三栏视图收起这些侧面部件，优先保证道路与仪表空间。左右后视镜使用同一 Three.js 场景的后向摄像机，显示刚驶过的道路、树木与路牌背面，随车速同步移动。镜面各自最多以 20 fps、360 px 宽渲染，隐藏时停止绘制。切换全屏后立即重绘前方视图，避免尺寸变化时短暂空白。

路牌采用有厚度的金属背板，立杆位于背板后方，正面标识与杆体保持间距，修复了 80 限速牌的杆子穿过圆盘问题。

门锁初始显示“四门已锁”，与左侧控制按钮的初始状态一致；收到门锁 CAN 报文后覆盖对应状态。默认显示本身不会发送报文。

行程由仿真车速积分计算，仅在连接 CAN 且车辆移动时累计；平均车速按累计行程和行驶时间计算，停车不计入行驶时间，刷新页面归零。

右侧转速表范围为 **0–8000 r/min**，6500 起为红区。现有 CAN 协议没有发动机转速信号，因此转速来自 `web/src/engine-model.js` 的六挡自动变速箱视觉模型：根据接收后的仿真车速、加减速和传动比计算，升挡后转速回落，停车时保持约 800 r/min 怠速，断开 CAN 时回零。这是演示值，不是 ECU 实测值，也不会向总线额外发送转速帧。将来接入真实转速信号时可替换该模型。
