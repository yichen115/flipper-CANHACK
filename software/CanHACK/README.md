# CANHACK 使用说明

## 快速演示

1. 启动 `software/cluster_demo` 后端并连接 CAN，波特率设为 500 kbit/s。Flipper 的晶振配置须与 CAN 扩展板一致。
2. 打开 CANHACK。程序自动开启设备 GPIO 菜单中的 **5V on GPIO**，退出后关闭。
3. 在 `UDS Services → Settings` 设置 REQUEST ID `721`、RESPONSE ID `728`，输入框为十六进制。
4. 选择 `ECU Info / VIN`，直接读取会话、软件版本、完整 17 字节 VIN、零件号、序列号和硬件版本。
5. 选择 `DID Scanner → Default (0x01) → Quick ID (F180-F1A0)`，展示 DID 发现及完整数据。也可选择 Extended 会话；F186 应返回 `03`。
6. 选择 `Read / Clear DTC → Read DTC`，应显示 `123456 / 09` 和 `ABCDEF / 08`。确认清除后再次读取应为 0 条；`ECU Reset → Default (0x01) → Hard Reset` 或重连演示后端会恢复模拟故障码。

已知 ECU 地址时，可以直接读取信息与 DTC，无须先扫描总线。`ECU Info / VIN` 使用常见标识 DID，具体 ECU 可能只支持其中一部分；未支持的数据会显示 NRC。

## Capture / Sniffer 记录

Capture 和 Sniffer 共用异步日志线程：接收线程只将帧放入 **256 帧队列**，写盘线程使用 **2 KB 缓冲**批量写入 SD。退出时先停止接收，再排空队列、写入尾部数据并同步文件；写入失败会提示错误。

- `n` / `RX`：接收帧数；`hw` / `H`：观察到的 MCP2515 接收缓冲溢出标志次数，不能换算成精确丢帧数量。
- `q` / `Q`：软件队列已满而丢弃的帧数。队列仅吸收短时写盘延迟，不能保证满负载总线无丢帧；MCP2515 自身仍只有两个接收缓冲。
- Sniffer 地址列表最多显示 **100 个标准/扩展 ID 组合**，达到上限显示 `LIMIT`；`Save All` 仍会记录其他 ID。
- 打开/退出地址详情时保持同一个 CAN 接收线程，`Save All` 持续记录完整总线。`Only Address` 在详情页记录选中的 ID/帧类型，切换时需要关闭/创建文件，仍可能产生接收空隙。
- 日志没有固定帧数上限，受 SD 剩余空间和文件系统限制；连续记录性能需要使用实际扩展板和 SD 卡测量。

每帧记录软件读取完成时的相对时间，保留原来的整数毫秒字段，并增加 `:Uxxx` 微秒余数。例如：

```text
r:0:1234:721:2:01 02:U567
r:0:1234:721:2:00 00:Q1:U890
```

第一条时间为 `1,234,567 µs`；`Q1` 表示 RTR，其数据字段仅为占位值。相邻帧的时间戳差就是记录的间隔。**微秒是记录分辨率，不代表总线到达时间具有微秒测量精度**：SPI、任务调度和硬件缓冲都会影响它。收发任务运行期间阻止深度休眠，利用系统 tick 与 SysTick 硬件计数器计时，任务结束后释放休眠限制。

Replay 可读取新日志和没有 `U` 后缀的旧日志。现有 CSV 导出仍使用整数毫秒，不保留微秒余数和 RTR 标记；需要这些信息时请使用原始 `.log`。

## Replay / Sender 发送

Replay 的 `Real` 按整段日志的目标时间发送，避免把读文件与发送耗时不断叠加到下一帧间隔；第一帧立即发送。`Fast` 将每段大于 20 ms 的间隔压至 20 ms。`late` 统计开始发送前迟到超过 1 ms 的帧数，`bad` 统计跳过的格式错误或时间倒退记录；调度无法保证补偿 SD 阻塞或忙碌总线造成的延迟。`Loop` 在上一轮结束后立即开始下一轮。

Replay 只在三个 TX 缓冲都忙、确认尚未提交帧时进行有限重试；其他发送错误会停止播放，防止超时后重复提交同一帧。读取文件失败也会结束并显示失败。

Sender 的 `REPEAT` 使用 32 位整数次数，修复超过 255 次溢出，界面最多可配置 `100 × 100000 = 1000 万` 次尝试。周期发送以固定时间网格安排，错过的周期直接跳过；显示已尝试、成功和错误数量，BUS-OFF、SPI 错误或发送状态不确定时停止。BACK 可取消等待并结束工作线程。

底层 MCP2515 改用批量 SPI 装载/读取 CAN 帧，以 TXnIF 确认发送成功；发送超时会撤销该发送缓冲的 TXREQ，并检查恰好发送完成的竞争情况。双接收缓冲轮流读取，修正标准 RTR 判断，并移除 READ RX BUFFER 后可能误清新帧的二次中断清除。本轮涉及的菜单切换通过事件队列完成，避免在控件回调持锁时重建页面。

## ECU Discovery

- 默认范围 `600–7FF`，仅扫描标准 11 位 CAN ID。支持设置范围；扫描完成后选择一个 TX → RX 配对，会自动应用到 UDS Settings。
- `Wait / ID` 可选 **10 / 25 / 50 / 100 ms**，默认 10 ms。收到候选响应即进入复查，不继续耗尽该 ID 的等待时间。
- 通过服务、会话回显、CAN 帧类型与重复请求复查减少误报；独立发现最多保留 32 个配对，ALLINONE 最多 16 个。
- 显示扫描进度和耗时；按 BACK 取消。响应慢的 ECU 请用 50 或 100 ms 重扫，10 ms 可能漏检。
- 512 个无响应 ID 的等待时间约为 `512 × Wait / ID`，还需加 SPI、界面更新、复查和调度开销；独立 Discovery 每个 ID 另让出 1 ms。实际速度须在硬件上测量。

## UDS 请求和扫描

`Settings → Response wait` 可选 **10 / 50 / 100 / 500 ms**，默认 50 ms。`Request gap` 可选 **0 / 5 / 20 / 50 ms**，默认 5 ms，用于服务扫描、DID 扫描和 ECU Info 的请求间隔；ALLINONE 的 DID 阶段也使用该设置。Discovery 的等待时间单独设置。

独立服务与 DID 扫描已取消旧的固定等待，收到有效响应后即可进入下一项。没有响应仍须等待超时，完整扫描所有 DID 依然可能很久；优先使用 Quick ID 或特定范围。

共用通信层支持经典 CAN 的 ISO-TP 单帧与多帧请求/响应，包括序号检查、块流控、STmin、超时和取消。每次请求/响应载荷上限 **512 字节**，支持标准和扩展 CAN ID 的普通寻址；不支持 CAN FD、扩展寻址和 DoIP。旧手动发送界面仍保留最多 100 字节输入；接收容量由“Frames to get”决定，且最多 512 字节。帧数不足会报失败，不返回截断成功。

收到 NRC `78` 后按 P2* 继续等待，默认 5 秒；会话正响应中的 P2/P2* 参数会应用于当前通信实例。连续帧等待上限 1 秒，单次事务总等待最多 15 秒。超过容量会报告错误，长响应会发送流控溢出通知，不作为完整读取成功。

只有校验通过的会话正响应才标记切换成功。进入后续读取/扫描时，非默认会话会重新确认，避免在菜单停留后 ECU 会话已过期。长扫描由拥有当前 CAN 控制器的工作线程发送 TesterPresent；不再使用另一个定时器并发访问重新初始化中的控制器。

服务扫描发送 SID 探测：正响应或 NRC `13` 等可以表明服务存在，但不代表该服务的所有参数都可用。NRC `11` 不计入支持证据。DID 扫描只将匹配 DID 的正响应计为发现；NRC `31/11/12` 不再显示成发现条目，其他 NRC 单独显示。通用 NRC 不携带 DID，因此无法绝对区分同一 ECU 对前后两个请求的延迟负响应。

## 结果与退出

- DID 的完整 HEX/ASCII 结果实时写入应用数据目录的 `logs/DID_*.txt`，屏幕仅保留有限历史，避免全范围扫描不断占用内存。取消时关闭文件并保留已写入内容；写入失败会提示部分日志，无 SD 日志时仍可查看屏幕结果。
- ALLINONE 的会话/DID 阶段使用共用通信层，报告保存至 `logs/ALLINONE_*.txt`，包含已读取 DID 的 HEX 数据。原有安全测试阶段保留其尝试策略，不保证与独立扫描具有同样的耗时。
- DTC 页面显示完整 24 位代码与状态字节，最多容纳 512 字节 UDS 载荷中的 127 个 DTC。超过容量明确报错，不自动截断；清除前需要在界面确认。
- BACK 会向 UDS 工作线程发出停止标志，再等待清理控制器。取消不能撤回已发送的请求。底层 SPI/CAN 发送或存储操作中的一次阻塞仍需先返回。

## 构建与验证

在本目录执行 `ufbt`，生成 `dist/canbus_hack.fap`。当前构建目标为 Flipper F7、固件 API 88.2；其他固件可使用其对应 SDK 重新构建。

在仓库根目录执行：

```powershell
python -m unittest discover -s software/tests/canhack -p 'test_*.py' -v
```

当前包含 **19 项 CAN 收发/记录测试 + 19 项 UDS 测试**。CAN 测试编译实际驱动、日志编解码与异步记录器，通过 SPI 寄存器模拟和真实主机线程验证发送完成/超时撤销、初始化 SPI 故障、接收缓冲/RTR、旧日志兼容、计时回绕、回放无累计漂移、慢写盘队列溢出及最终排空。

UDS 测试将实际的 `uds_transport.c` 编译为临时动态库，覆盖错误帧注入、超时及计时回绕、NRC 78、取消、多帧双向流控和序号回绕，并通过虚拟 CAN 与 `cluster_demo` 后台 ECU 联调 VIN、DTC、清除与复位。Windows 需要 MSVC Build Tools；其他系统需要 C11 编译器 `cc` 和支持 C++17 的 `c++`。虚拟 CAN 联调依赖 `software/cluster_demo/requirements.txt`。

后端原有回归在 `software/cluster_demo` 下执行：

```powershell
python -m unittest discover -s tests -p 'test_*.py' -v
```

这些测试覆盖主机上的 C 通信层与演示后端；Flipper 界面、真实 MCP2515 时序及繁忙总线中的丢帧/吞吐仍需真机验证。
